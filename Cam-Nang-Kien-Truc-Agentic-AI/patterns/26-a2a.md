# 26. A2A (Agent-to-Agent Protocol)

[← Về mục lục chính](../README.md)

## 1. Tên pattern

A2A — chuẩn giao thức mở hoá tương tác agent-to-agent, cùng 12 pattern triển khai: Direct agent
invocation, Agent registry discovery, Brokered A2A, A2A task delegation, Long-running task,
Streaming progress, Artifact exchange, Human-in-the-loop task, Agent federation, Cross-organization
agent collaboration, A2A gateway, A2A plus MCP composition.

## 2. Vấn đề cần giải quyết

MCP (file 25) chuẩn hoá agent-to-tool/data, nhưng không giải quyết trường hợp một agent cần nhờ
**một agent khác** thực hiện một phần công việc — đặc biệt khi agent kia thuộc tổ chức khác, chạy
trên nền tảng khác, và không muốn (hoặc không thể) công khai internal memory, prompt hay tool
implementation của mình. A2A giải quyết bằng cách chuẩn hoá một giao thức cho phép agent gọi agent
khác qua ranh giới tổ chức/nền tảng, chỉ trao đổi task, artifact và message — không cần biết agent
kia được xây dựng như thế nào bên trong.

## 3. Bối cảnh sử dụng

Hệ thống cần giao việc cho một agent chuyên biệt không thuộc quyền kiểm soát trực tiếp của mình
(agent của đối tác, agent của phòng ban khác, agent bên thứ ba cung cấp dịch vụ) — khác với việc gọi
sub-agent nội bộ cùng một hệ thống (nơi native orchestration đơn giản hơn thường phù hợp hơn).

## 4. Kiến trúc

```
Client Agent
    ↓
Agent Card Discovery   (agent kia công khai "danh thiếp" mô tả năng lực)
    ↓
Send Task
    ↓
Remote Agent Processing
    ↓
Progress / Artifact / Result
```

## 5. Thành phần

Agent Card (mô tả năng lực agent, công khai để discovery); Task object (đơn vị công việc gửi cho
remote agent); Artifact (sản phẩm remote agent trả về); Message (trao đổi qua lại trong quá trình xử
lý); Registry/Broker (nếu dùng discovery gián tiếp — mục 26.2, 26.3).

## 6. Luồng xử lý chi tiết

**12 pattern triển khai:**

- **Direct agent invocation (26.1)**: client agent biết trước địa chỉ/agent card của remote agent,
  gọi thẳng không qua trung gian — đơn giản nhất, phù hợp khi quan hệ giữa hai agent đã cố định.
- **Agent registry discovery (26.2)**: client agent tra cứu một registry trung tâm để tìm agent phù
  hợp với năng lực cần thiết, không cần biết trước địa chỉ cụ thể — cho phép thêm/bớt remote agent
  mà không cần sửa client.
- **Brokered A2A (26.3)**: một broker trung gian nhận task từ client, tự chọn remote agent phù hợp
  (có thể dựa trên tải hiện tại, chi phí, độ tin cậy) rồi chuyển tiếp — client không cần tự quyết
  định chọn agent nào.
- **A2A task delegation (26.4)**: client gửi một task hoàn chỉnh cho remote agent xử lý độc lập,
  không can thiệp vào cách remote agent thực hiện bên trong, chỉ quan tâm kết quả trả về.
- **Long-running task (26.5)**: tương tự Long-running MCP task (mục 25.7) nhưng cho agent-to-agent
  — remote agent trả handle, client theo dõi tiến độ qua polling hoặc streaming thay vì chờ đồng bộ.
- **Streaming progress (26.6)**: remote agent chủ động đẩy cập nhật tiến độ trong lúc xử lý (thay vì
  chỉ trả kết quả cuối), cho phép client hiển thị tiến độ thực tế hoặc can thiệp sớm nếu cần.
- **Artifact exchange (26.7)**: kết quả trao đổi giữa hai agent là artifact có cấu trúc rõ ràng
  (không chỉ text tự do) — cho phép client xử lý kết quả một cách có chương trình thay vì phải diễn
  giải ngôn ngữ tự nhiên.
- **Human-in-the-loop task (26.8)**: task A2A có điểm dừng cần con người phê duyệt/cung cấp thông
  tin bổ sung giữa chừng — remote agent tạm dừng, chờ input, rồi tiếp tục.
- **Agent federation (26.9)**: nhiều agent thuộc các domain/tổ chức khác nhau hợp tác qua A2A trong
  khi mỗi bên vẫn giữ quyền kiểm soát độc lập với agent của mình — liên hệ trực tiếp Federated
  multi-agent (file 12), A2A là giao thức kỹ thuật hiện thực hoá pattern đó qua ranh giới tổ chức.
- **Cross-organization agent collaboration (26.10)**: biến thể của federation nhấn mạnh khía cạnh
  hợp đồng/tin cậy giữa các tổ chức khác nhau (không chỉ domain khác nhau trong cùng tổ chức) — cần
  cơ chế xác thực và giới hạn phạm vi chặt chẽ hơn.
- **A2A gateway (26.11)**: điểm vào tập trung xử lý routing, authentication, rate limiting cho các
  yêu cầu A2A tới nhiều remote agent khác nhau — tương tự MCP gateway (mục 25.3) nhưng cho tầng
  agent-to-agent.
- **A2A plus MCP composition (26.12)**: kết hợp cả hai chuẩn trong cùng một hệ thống — remote agent
  nhận task qua A2A, rồi chính remote agent đó dùng MCP để gọi tool/dữ liệu cần thiết nhằm hoàn
  thành task — hai chuẩn giải quyết hai tầng khác nhau và bổ sung cho nhau.

## 7. State và dữ liệu

Task state (đang xử lý/hoàn thành/lỗi) do remote agent quản lý và expose qua giao thức; client agent
chỉ cần lưu task ID để theo dõi, không cần (và không nên) biết chi tiết state nội bộ của remote
agent.

## 8. Thuật toán liên quan

Không có thuật toán ML riêng — là chuẩn giao thức cho tương tác agent-to-agent.

## 9. Cách triển khai

1. Xác định rõ ranh giới: task nào nên giao cho sub-agent nội bộ (native orchestration, đơn giản
   hơn) và task nào thực sự cần A2A (agent thuộc tổ chức/nền tảng khác, cần ranh giới rõ ràng về
   những gì được công khai).
2. Thiết kế Agent Card mô tả năng lực đủ rõ để client agent (hoặc registry) chọn đúng remote agent
   phù hợp cho task.
3. Dùng Artifact có cấu trúc (mục 26.7) thay vì text tự do cho kết quả cần xử lý tiếp theo chương
   trình — giảm rủi ro diễn giải sai.
4. Với task có điểm dừng cần con người (mục 26.8), thiết kế rõ cơ chế tạm dừng/tiếp tục, không giả
   định task luôn chạy liền mạch từ đầu tới cuối.
5. Khi hợp tác cross-organization (mục 26.10), thoả thuận rõ về xác thực, giới hạn phạm vi, và cam
   kết chất lượng dịch vụ trước khi tích hợp kỹ thuật.

## 10. Tham số cần tuning

Timeout cho mỗi task; tần suất polling hoặc cấu hình streaming cho long-running task; giới hạn số
task đồng thời gửi tới một remote agent.

## 11. Failure modes

- **Chọn A2A cho sub-agent nội bộ**: dùng giao thức A2A đầy đủ cho tương tác giữa các agent trong
  cùng một hệ thống nội bộ tạo overhead không cần thiết so với native orchestration đơn giản.
- **Agent Card mô tả không chính xác năng lực thực tế**: client gửi task remote agent không xử lý
  tốt được, dẫn tới lỗi hoặc kết quả kém chất lượng.
- **Không xử lý đúng long-running/streaming**: client chờ đồng bộ cho task lẽ ra cần theo dõi tiến
  độ, gây timeout hoặc trải nghiệm kém.
- **Human-in-the-loop task không có cơ chế timeout rõ ràng khi chờ input**: task treo vô thời hạn
  nếu không ai phản hồi điểm dừng.

## 12. Security considerations

A2A đặc biệt nhạy cảm ở ranh giới tổ chức (mục 26.9, 26.10) — cần xác thực identity của cả client và
remote agent, giới hạn rõ phạm vi dữ liệu được chia sẻ qua task/artifact, và không để remote agent
truy cập nhiều hơn phạm vi task cần thiết (liên hệ Least-privilege agent, mục 29.2). Identity
propagation (mục 29.1) cần xuyên suốt qua cả A2A gateway nếu dùng.

## 13. Observability

Trace xuyên suốt từ client agent qua remote agent, dù hai bên có thể thuộc hệ thống logging khác
nhau — cần correlation ID nhất quán truyền qua task để có thể ghép nối trace khi debug sự cố xảy ra
ở phía remote agent.

## 14. Evaluation metrics

Delegation success rate (tỷ lệ task giao cho remote agent hoàn thành đúng yêu cầu); độ trễ end-to-end
qua A2A so với xử lý nội bộ tương đương; tỷ lệ task cần con người can thiệp giữa chừng.

## 15. Ưu điểm

Cho phép hợp tác giữa các agent thuộc tổ chức/nền tảng khác nhau mà không cần công khai chi tiết
triển khai nội bộ, mở ra khả năng xây dựng hệ sinh thái agent liên tổ chức.

## 16. Nhược điểm

Thêm độ phức tạp giao thức và vận hành so với gọi sub-agent nội bộ trực tiếp; cần đầu tư vào xác
thực/quản trị ranh giới tổ chức để an toàn.

## 17. Khi nên dùng

Khi cần giao việc cho agent thực sự độc lập về mặt tổ chức/nền tảng, đặc biệt qua ranh giới doanh
nghiệp, hoặc khi muốn expose một agent như một dịch vụ có thể gọi bởi nhiều client khác nhau không
thuộc cùng hệ thống.

## 18. Khi không nên dùng

Giao tiếp giữa các sub-agent trong cùng một hệ thống nội bộ do một đội kiểm soát — native
orchestration (liên hệ Phần IV) đơn giản và hiệu quả hơn, không cần overhead của giao thức A2A đầy
đủ.

## 19. Pattern liên quan

Bổ sung trực tiếp cho MCP (file 25) — A2A là agent→agent, MCP là agent→tool/data, thường kết hợp
(mục 26.12); hiện thực hoá kỹ thuật cho Federated multi-agent (file 12) và Cross-organization
collaboration (mục 26.10); liên hệ Handoff (Phần IV) cho chuyển giao trong cùng hệ thống.

## 20. Ví dụ kiến trúc thực tế

Nền tảng logistics của công ty A cần agent định giá vận chuyển của đối tác vận tải B (thuộc tổ chức
khác, không muốn công khai logic định giá nội bộ): agent A gửi task qua A2A gateway kèm thông tin lô
hàng, agent B xử lý độc lập (có thể dùng MCP nội bộ để tra cứu giá nhiên liệu, tuyến đường — mục
26.12) và trả về artifact có cấu trúc (bảng giá, thời gian dự kiến); nếu giao dịch giá trị lớn, task
có điểm dừng human-in-the-loop (mục 26.8) trước khi xác nhận cuối cùng.
